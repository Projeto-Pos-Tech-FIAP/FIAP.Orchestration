1. Visão Geral da Plataforma

Implementação do Consumer (PaymentProcessedConsumer)

O PaymentProcessedConsumer é um BackgroundService registrado no IHostedService do ASP.NET Core. Ele roda em background enquanto a API está ativa e processa cada mensagem do tópico payment-processed:

  1. Consome a mensagem com manual commit (offset só avança após processamento bem-sucedido)
  2. Desserializa o PaymentProcessedEvent do JSON
  3. Se Status == "Approved": cria a Library do usuário (se não existir) e adiciona o LibraryGame
  4. Se rejeitado: apenas loga o motivo — nenhuma ação no banco
  5. Em caso de erro: espera 2s e retenta (não perde o offset)

5. Containerização com Docker

Dockerfile — Multi-Stage Build

O Dockerfile usa multi-stage build com duas etapas para reduzir o tamanho da imagem final de ~600MB para ~100MB: 

# Stage 1: SDK (compila e publica)
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
# Copia só os .csproj primeiro → layer cache para restore
COPY src/.../*.csproj ...
RUN dotnet restore

COPY . .
RUN dotnet publish -c Release -o /app/publish /p:UseAppHost=false

# Stage 2: Runtime (apenas o necessário para executar)
FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
# Cria usuário não-root por segurança
RUN adduser --system appuser
USER appuser

COPY --from=build /app/publish .
EXPOSE 8080
ENTRYPOINT ["dotnet", "FIAP.CatalogAPI.Api.dll"]
StageImagem baseTamanhoFinalidade
builddotnet/sdk:10.0~600MBCompilar e publicar o projeto
finaldotnet/aspnet:10.0~80MBExecutar a aplicação em produção
✅ Boas Práticas Aplicadas Cache de layers (copia .csproj antes do source), .dockerignore excluindo bin/ e obj/, usuário não-root, imagem mínima de runtime, UseAppHost=false para evitar binário nativo desnecessário.

6. Orquestração com Kubernetes

Namespace

Todos os recursos são criados no namespace fiap-games, isolando o ambiente dos outros workloads do cluster.

Separação ConfigMap vs Secret

TipoO que armazenaExemplos
ConfigMap Dados não-sensíveis, configurações de comportamento Tópicos Kafka, hostname do MongoDB, environment, GroupId
Secret Dados sensíveis, credenciais, connection strings Senha do SQL Server, connection string completa, senha do MongoDB

Hierarquia de ConfigMaps

Cada Pod recebe dois ConfigMaps via envFrom, o que evita duplicação de configurações compartilhadas:

Pod catalog-api ├── envFrom: shared-infra-config ← Kafka topics, Redis, MongoDB host (TODOS usam) ├── envFrom: catalog-api-config ← GroupId e DatabaseName específicos do serviço └── envFrom: catalog-api-secret ← Connection string SQL, senhas (Secret)

Deployments vs Pods Isolados

Todos os workloads usam Deployment, que garante:

  • Self-healing: se um Pod cai, o ReplicaSet cria outro automaticamente
  • Rolling updates: atualização sem downtime com kubectl set image
  • Rollback: kubectl rollout undo deployment/catalog-api
  • Scaling: kubectl scale deployment/catalog-api --replicas=5

Comunicação Entre Serviços no Cluster

Dentro do cluster Kubernetes, os pods se comunicam usando os nomes dos Services como hostname DNS — sem necessidade de IPs:

8. Como Executar — Docker Compose

O docker-compose.yml em FIAP.Orchestration/ sobe toda a stack com healthchecks e dependências corretas.

Passo a Passo

# 1. Entrar na pasta de orquestração
cd C:\Users\mathf\source\repos\FIAP.Orchestration

# 2. Subir toda a stack (infra + CatalogAPI)
docker-compose up -d

# 3. Acompanhar os logs
docker-compose logs -f catalog-api

# 4. Verificar status de todos os containers
docker-compose ps

# 5. Parar tudo mantendo volumes
docker-compose down

# 6. Parar e remover volumes (reset completo)
docker-compose down -v

9. Como Executar — Kubernetes

Pré-requisitos

  • Cluster local rodando: Docker Desktop (K8s habilitado), Kind, Minikube ou k3d
  • kubectl configurado (kubectl cluster-info deve retornar OK)
  • Kustomize integrado ao kubectl 1.14+ (kubectl apply -k)

Deploy Completo

# ── Passo 1: Build da imagem do CatalogAPI ──────────────────────────
cd C:\Users\mathf\source\repos\FIAP.CatalogAPI
docker build -t fiap/catalog-api:latest .

# ── Passo 2: Se usar Kind ou k3d, carregar a imagem no cluster ───────
kind load docker-image fiap/catalog-api:latest
# ou para k3d:
k3d image import fiap/catalog-api:latest -c <nome-do-cluster>

# ── Passo 3: Aplicar todos os manifestos com Kustomize ───────────────
cd C:\Users\mathf\source\repos\FIAP.Orchestration
kubectl apply -k k8s/

# ── Passo 4: Aguardar pods iniciarem ─────────────────────────────────
kubectl get pods -n fiap-games -w

# ── Passo 5: Port-forward para acessar a API ─────────────────────────
kubectl port-forward svc/catalog-api 5001:80 -n fiap-games
# Abrir: http://localhost:5001/swagger

Comandos Úteis de Diagnóstico

# Ver todos os recursos no namespace
kubectl get all -n fiap-games

# Ver logs de um pod específico
kubectl logs -f deployment/catalog-api -n fiap-games

# Ver eventos de um pod com problema
kubectl describe pod <nome-do-pod> -n fiap-games

# Escalar o CatalogAPI para 3 réplicas
kubectl scale deployment/catalog-api --replicas=3 -n fiap-games

# Atualizar imagem (rolling update sem downtime)
kubectl set image deployment/catalog-api catalog-api=fiap/catalog-api:v2 -n fiap-games

# Rollback em caso de problemas
kubectl rollout undo deployment/catalog-api -n fiap-games

# Remover tudo
kubectl delete -k k8s/
⚠️ Sobre Secrets em Produção Os arquivos secrets/*.yaml contêm credenciais em texto plano com stringData. Para ambientes reais, use Sealed Secrets, External Secrets Operator ou HashiCorp Vault — e nunca commite credenciais reais no Git.

Melhorias Sugeridas para Produção

  • Adicionar Ingress (Nginx/Traefik) para expor APIs externamente com TLS
  • Substituir Deployments de banco por StatefulSets para melhor gerenciamento de estado
  • Usar Sealed Secrets ou External Secrets Operator para secrets seguros em Git
  • Adicionar HorizontalPodAutoscaler para escala automática baseada em CPU/memória
  • Configurar PodDisruptionBudget para manter disponibilidade durante atualizações
  • Adicionar NetworkPolicy para isolar comunicação entre namespaces
  • Subir Kafka para 3 brokers com fator de replicação 3 para alta disponibilidade
